# AiWardrobe 优化方案：可信的购买决策与持续反馈

日期：2026-10-01。性质：优化实施前的证据与路线记录。
代码基线：`f2deaec`。依据：当前前后端代码、测试、现行产品规范和历史设计文档。

本文中的问题证据描述 `f2deaec` 基线，不表示这些缺口目前仍然存在。实现范围与当前验证状态见[实施计划](superpowers/plans/2026-10-01-aiwardrobe-optimization.md)；目标行为、数据契约和验收以[优化 Spec](superpowers/specs/2026-10-01-aiwardrobe-optimization-spec.md)为准。

## 1. 建议与范围

继续围绕「购买前 AI 衣橱决策助手」推进，优先让每次分析可靠、可解释、可回看，并让用户反馈影响下一次建议。

当前已经具备买前分析首页、商品 URL/图片分析、候选确认入库、衣柜报告、缺口推荐、轻量偏好、指定单品搭配入口、天气、收藏和搭配历史。指定单品目前在生成后追加，约束质量仍需完善。下一轮应提高这些能力的质量，避免重复排期。

用户提到最初参考了三个项目。当前仓库及全部可达 Git 历史没有保存三个项目的名称、URL 或源码目录；尚不能完成这三个项目的逐项对照。历史方案引用的 `docs/1.txt`～`docs/4.txt`、`docs/FEATURES.md` 不在当前目录或 Git 历史对象中。

下文使用当前代码形成可实施建议；搭搭、XZ 仅作为历史文档明确点名的补充产品参考，不等同于用户所指的三个原始项目。原始资料恢复后，应补充「参考能力 → 本项目现状 → 可迁移方案」对照，复核下文优先级。

## 2. 三种推进路线

| 路线 | 主要投入 | 收益与代价 | 建议 |
|---|---|---|---|
| A：可信分析与反馈闭环 | 真实链路、数据边界、候选历史、反馈落库 | 直接改善核心价值；需要前后端及少量数据模型调整 | 优先采用 |
| B：扩充功能与渠道 | 试衣、社区、小程序、会员、复杂日历 | 扩大入口与功能面；现有分析质量问题仍会传递到新入口 | 核心链路验证后再选一个方向 |
| C：先重构基础架构 | 微服务、全量缓存、多模型热备、弹性扩容 | 有利于明确的规模需求；目前缺少负载、成本和失败率基线 | 做持久任务、分页、迁移等必要改进，其余按测量结果引入 |

路线 A 的成功标准是：用户能理解为什么建议买或不买，能找到对应衣物，能恢复过去的决定，反馈能改变后续建议。

## 4. P0：先让真实使用可靠

### 4.1 区分真实结果、演示结果和失败

证据：[ai.py](../backend/app/ai.py#L100) 在远端识别异常后回退到按文件名生成的 Demo，Demo 置信度固定为 0.82；[uploads.py](../backend/app/routers/uploads.py#L57) 会直接写入 `ready/confirmed`。

建议保留 Demo 供开发和体验展示，生产识别失败返回明确错误或待确认结果。持久化 `analysis_source`、provider、模型/规则版本、生成时间和错误码；演示来源不能覆盖成看似真实的上传来源。低置信度字段提示修正，未经确认的结果不作为可靠的个性化证据。模型自报置信度先视为提示值，需人工样本校准后才能解释为准确概率。

验收：超时、非法 JSON、缺少凭证三类场景均不会悄悄产出已确认的示例衣物；用户能重试或手动补录；真实结果与演示结果在 API 和界面中可区分。

### 4.2 补通商品推荐真实图片分析

证据：[shopping_recommendations.py](../backend/app/shopping_recommendations.py#L354) 的图片输入函数在非 Demo 模式直接抛出 `image_download_failed`。淘宝搜索接口的存在不代表推荐分析全链路可用。

实现共享的安全图片下载和规范化模块，商品 URL 分析与推荐商品分析复用。分别记录检索失败、图片失败、视觉标签失败和购买决策失败；一项失败不阻止其他成功项展示。商品标签缓存与用户决策缓存分开。

验收：关闭 Demo 后，在非付费的模拟服务契约测试中，有效商品图可以生成候选并继续完成决策；坏图只影响该项；原图、缩略图和来源有效。真实凭证验证另行执行，不以模拟测试代替真实服务验证。

### 4.3 将长耗时识别变成可恢复任务

证据：[uploads.py](../backend/app/routers/uploads.py#L67) 在请求内等待检测和标签全流程；处理中多为 `flush`，结束才 `commit`。RunningHub 配置允许最长 600 秒等待，现有查询接口无法充分解决刷新和进程重启问题。

先建立持久化任务及独立 worker；按部署规模选择数据库任务队列或成熟队列，不同时引入多个调度框架。上传数据保存并提交任务后返回 `202 + task_id`；前端轮询已有/扩展状态接口，后续才考虑 SSE。

任务状态使用 `queued/running/succeeded/failed/cancelled`，下载、预处理和识别作为独立阶段记录；任务成功与衣物是否经用户确认分别管理，识别成功仍可以生成待确认衣物。保存 provider task ID、尝试次数、阶段时间和本地幂等键；支持供应商幂等键时一起使用。

远端已受理但响应丢失，或本地写入远端 ID 前崩溃时，增加 `submission_unknown` 提交状态。能核验远端任务才恢复，无法核验时停止自动重提并提供查询或人工处理入口；本地幂等键不能保证供应商只执行一次。图片和数据库记录分清引用关系。

验收：小文件接收完成后，创建任务的响应目标为 2 秒内（待实际环境测量）；页面刷新可恢复进度；worker 重启后任务继续或明确终止；本地重复请求不重复入库；供应商支持幂等时验证重提只执行一次，未知受理状态不会自动发起第二次收费调用。重任务需要独立处理的方向与 [FastAPI 官方说明](https://fastapi.tiangolo.com/tutorial/background-tasks/) 一致。

### 4.4 收紧输入、身份和图片访问边界

证据：[product_extraction.py](../backend/app/product_extraction.py#L144) 仅检查 URL 协议并自动跟随重定向；[purchase.py](../backend/app/routers/purchase.py#L55) 全量读取上传；[main.py](../backend/app/main.py#L35) 公开挂载上传目录；[rate_limit.py](../backend/app/rate_limit.py#L22) 的过期清理不区分 scope，短窗口可能删除长窗口记录。

页面、重定向和图像地址统一检查解析后的 IP，拒绝本机、私网和元数据地址，控制重定向次数及下载字节数；图片验证真实格式和像素上限，清理 EXIF。URL 防护应覆盖 DNS 变化与实际连接目标，参考 [OWASP SSRF 指南](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)。

生产启动拒绝默认 JWT 密钥；登录、验证码和 AI 调用按用户/IP 等边界限流；修复分 scope 保留与并发原子性。衣物图使用鉴权路由或私有存储短期签名；共享图片仅在最后一个引用删除后清理。上述为代码边界建议，未核实生产部署是否使用默认配置。

验收：直接及重定向私网地址被拒绝；伪图片和超限文件在 AI 调用前被拒绝；不同窗口不会相互清空；并发不能突破调用额度；持有过期或未授权图片链接无法访问私人照片。

## 5. P1：把购买建议变成可核验的决策

### 5.1 规则负责约束，模型负责标签与解释

证据：[purchase_analysis.py](../backend/app/purchase_analysis.py#L63) 的分数主要来自品类数量和标签规则；偏好只是进入解释事实；搭配潜力统计品类数量，[搭配方案](../backend/app/purchase_analysis.py#L327) 仅含候选本身且图片为空；[建议价](../backend/app/purchase_analysis.py#L296) 来自品类常量和分数。

建议沿用可解释规则，先补预算、明确避开类型、用户场景和风格约束，再调整软性匹配权重。提供「基于 X 件已确认衣物、Y 项偏好」的数据覆盖说明。未提供足够衣橱数据时，重复风险和搭配潜力标记依据不足，提供通用场景建议，不伪装成充分的个人分析。

结果以一句结论、主要证据和可执行动作开头；分数作为辅助。每个相似项可打开真实衣物；搭配引用当前用户实际拥有的 garment IDs 和图片，缺少单品明确标为缺失。没有合理组合时不强行给出 2～3 套。

价格显示实际商品价、用户预算和计算来源；缺数据时请求补充或隐藏精确建议价。闲置风险称为规则估计，不能等同于未来穿着的已测概率。

指定已有单品搭配也需一致约束：[outfits.py](../backend/app/routers/outfits.py#L41) 当前先生成，再追加目标单品。应在生成前传入目标、类别和用户约束，生成后校验目标存在、同类组合合理，并让解释对应最终组合。

验收：同候选在不同预算或禁选条件下产生合理变化；所有引用归属于当前用户且状态有效；空衣橱不输出确定的重复/互补结论；指定单品不会仅靠事后追加形成冲突组合；模型解释不更改规则结论，不增加无依据的价格或搭配事实。

### 5.2 恢复候选历史并分离购买决定

证据：[PurchaseAnalysisView](../frontend/src/App.tsx#L954) 只保留局部候选状态；[HistoryView](../frontend/src/App.tsx#L1886) 只有搭配历史。后端保存了候选，但缺少可恢复的完整前端路径。

先提供候选列表/详情 API 与购买历史视图，复用现有历史导航中的分类。分析完成即保存结果；用户可标记待考虑、跳过、已购买和退货。处理状态、购买决定与是否已入衣橱分开存储，避免一个 status 承担多种含义。

按钮区分「保留候选」「确认已拥有并加入衣橱」。冷静器先用下次访问时的提醒，无需一开始接入推送服务。旧结果展示衣橱/偏好版本，用户可用当前资料重新分析并查看变化。

验收：刷新、切换页面和换设备能恢复候选；未确认拥有的商品不进入衣橱统计与搭配池；候选到衣物的唯一关联和原子操作保证并发确认只入库一次；删除已有衣物后旧搭配显示失效项并允许重新生成。

### 5.3 反馈落库后再讨论动态画像

证据：[App.tsx](../frontend/src/App.tsx#L1688) 的负反馈仅写 localStorage，未按账号隔离，后续生成请求不消费。

新增反馈事件，关联用户、候选/搭配、算法版本、反馈类型与可选原因。满意、收藏、实际穿过和购买是不同信号；不要把收藏直接当成满意或穿着。先将用户明确的负约束用于下一次筛选或排序，并提供撤销。

增加轻量「今天穿了」记录，带日期、衣物/搭配 ID、可选场景。穿着次数和最近穿着由事件计算；数据不足时报告显示未形成使用记录。[wardrobe_report.py](../backend/app/wardrobe_report.py#L32) 当前 `low_use_items` 永远为空，可在这一步形成真实功能。

验收：账号、设备间的数据边界正确；明确不喜欢的条件影响下一次结果；记录撤销能还原统计；只有实际购买价格和穿着事件齐全时才计算每次穿着成本。

### 5.4 降低首次体验和录入成本

证据：[App.tsx](../frontend/src/App.tsx#L242) 登录前直接显示登录页；批量和购买图片有压缩，普通单图/自动识别仍直接提交；[imageCompression.ts](../frontend/src/imageCompression.ts#L1) 只处理 JPEG，未按像素缩放。

先开放无需注册的首页与明确标为样例的完整分析，让用户理解价值。匿名真实分析试用在限流、配额和隐私生命周期完成后小范围验证；保留候选或关联衣橱时登录，并接续输入上下文。

只引导录入 3～5 件真实常穿衣物即可开始个性化体验；数量是引导目标，充分性仍取决于品类和场景。提供基础款示例时，让用户确认确实拥有，示例与真实数据隔离。

统一所有上传入口的格式、尺寸和质量策略；批量限制并发、逐项展示失败和重试；区分空衣橱、筛选无结果、少量衣物和加载失败。将 RunningHub/VL 等技术名词从普通操作文案改为用户能理解的识别方式与耗时说明。

验收：未注册用户能理解价值；登录后输入不丢；失败只重试失败项；大 PNG/WebP 有明确策略；有衣服但筛选无结果时提供清除筛选，不能提示首次上传。

## 6. P1/P2：工程效率与规模准备

按 auth、wardrobe、purchase、outfits、reports、shopping 逐步拆分约 2,000 行的 `App.tsx`，共享表单、结果卡和请求错误；引入能恢复详情和浏览器前进/后退的路由。`ApiError` 保留 HTTP 状态、业务 code、retry_after；批量删除显示逐项成功/失败，避免部分成功后列表仍残留全部项目。

现有图片懒加载保留，新增服务端分页、稳定排序和服务端过滤。先验证 500～2,000 件衣物的首屏与过滤，再决定是否需要虚拟列表。按页面拆分和需要加载资源，可参考 [React lazy 文档](https://react.dev/reference/react/lazy)。构建当前主 JS 约 203.78 kB，gzip 约 63.14 kB，尚没有证据需要全面重写前端。

字体已本地化，构建输出包含大量字重、语言子集与 woff/woff2；按实际使用的字重和语言收敛导入。当前 Cormorant/Montserrat 实现与项目 Plus Jakarta Sans 约定需作一次明确取舍，中文界面重点检查中文字体回退和阅读效果。

建立版本化迁移，替换启动时零散的 ALTER；新增 PostgreSQL 新库及旧库升级测试。当前 SQLite 迁移工具未覆盖偏好、购买候选和推荐记录，迁移策略需同步扩展。版本迁移机制可参考 [Alembic 官方教程](https://alembic.sqlalchemy.org/en/latest/tutorial.html)。

将商品视觉标签缓存与个人决策缓存拆开：后者使用衣橱 revision、偏好 revision、规则版本和有效期；衣橱变动只重算个人决策，避免重复视觉调用。记录任务分阶段耗时、错误来源、模型调用成本和降级次数。

验收：详情链接与浏览器返回有效；旧请求不会覆盖新页面/新账号状态；500 件衣物首次只读一页；过滤覆盖全量数据；新增相似衣物或修改预算后结论及时变化；旧 Postgres schema 可验证升级。

## 9. 验证与指标

本次实际运行的基线：后端 `python -m pytest -q` 为 **84 passed**；前端 `npm test` 为 **30 passed**；`npm run build` 成功。测试以 SQLite、Demo 与 mock 为主；未验证真实淘宝、RunningHub、ComfyUI、模型效果、生产 PostgreSQL 升级或真实浏览器体验。

下一轮优先补：非 Demo 商品图契约；模型超时/非法结果；任务重启与重复提交；私网/重定向 URL；候选跨页面恢复；不同账号反馈隔离；部分删除失败；偏好改变决策；Postgres 迁移；移动端与键盘完整流程。

建议事件漏斗：进入首页 → 提交候选 → 分析完成 → 查看证据 → 保留/跳过/确认拥有 → 后续反馈。看完成率、首次结果所需时间、7 日再次分析率和反馈覆盖率；先测基线，再设改进目标，不直接套用六月方案中的增长数字。

AI 指标区分视觉标签正确率、真实衣物引用正确率、证据完整性、用户采纳及后续满意度；构建 50～100 条包含空衣橱、重复款、预算冲突、禁选类型和错误标签的人工评审样本。买/不买没有唯一客观答案，不用“购买建议准确率”单一数字掩盖主观判断。

成本按真实成功分析统计，同时计入失败、重试与解释调用；监控异常降级率、任务 P50/P95、成功恢复率。只有完成实际购买决定反馈后，才统计用户自报减少重复购买的金额，并清楚标注数据来源。
